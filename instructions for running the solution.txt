1. DEMONSTRATION OVERVIEW

The demonstration uses two real phones, one vehicle VIN per phone, the Azure
Functions API, Azure SQL Database, and the browser dashboard. Phone readings
are captured locally, sent as JSON over HTTPS, processed/stored by the API,
and read back through API queries. Multiple vehicle cards show each VIN's
latest state and stored sessions separately.

Responsibilities:
- Ana: launch both mobile clients, configure distinct VINs, grant permissions,
  and verify acknowledgments/queued events.
- Stefana: verify API health, authorization, writes, and stored session data.
- Daniela: connect the dashboard, select both vehicles, and show historical
  session reports/charts/3D views.
- Adina: verify cloud addresses/settings, deployment, identity permissions,
  SQL setup, and CORS; retain evidence for the submission.

3. LAUNCH THE MOBILE APPLICATION - ANA

On the development computer, open a terminal in src/phone-app:

   npm start

For a clean reload after configuration/source changes:

   npx expo start -c

If LAN discovery of Metro is blocked, an optional development alternative is:

   npx expo start --tunnel

Open the QR code in compatible Expo Go on each physical phone. Keep Metro
running. The tunnel exposes Metro's development bundle; it does not expose a
separate local API. Both clients can use the same deployed Azure HTTPS API.

For phone 1:
1. Configure VIN WP0ZZZ99ZTS392124 (or the actual approved VIN for that phone).
2. Grant available motion/location permissions and enable location services
   when GPS position/route data is part of the demonstration.
3. Enter the ORIGINAL owner token in the token field. Do not enter its SHA-256
   hash, quotation marks, or the word Bearer. The app constructs the header.
4. Press 'Porneste trimiterea' / 'Pornește trimiterea' (Start sending).
5. Keep the app foregrounded and wait for acknowledgments. Move/tilt the phone
   gently to change sensor readings. GPS movement requires a location fix;
   rotating a stationary phone does not demonstrate a GPS route.

For phone 2, repeat with a DIFFERENT approved VIN, for example
WP0ZZZY1ZNSA54819. Both can use the same Porsche owner token when the server
entry permits both VINs. Do not reuse a VIN for two supposedly independent
vehicle streams: the VIN is sent as both deviceId and vehicleId.

The current capture interval is 2 seconds; hardware sensor samples are
requested every 500 ms. After stopping/reloading/reopening the app, check the
token input again because the UI token is stored only in memory.

4. CHECK THE PHONE'S DIAGNOSTICS

Tap the gear/settings control and inspect the diagnostic panel. Relevant
Romanian labels and expected observations:

- Motor / pornit: capture engine is on.
- Sesiune (cursa): the current session/trip identifier.
- Capturate in cursa: events captured during the current trip.
- In coada: pending queued events; it should drain as requests are acknowledged.
- Expediere: sending status. A blocked/error state requires attention.
- Ultima confirmare: last server acknowledgment, including event ID/status/time.
- API: the configured backend address; compare it with the actual Azure host.
- deviceId trimis: transmitted VIN, not the phone's internal diagnostic UUID.
- Retry: retry queued events after correcting configuration/authorization.
- Recalibrare altitudine: reset the relative-altitude baseline where supported.
- Inchide: close the diagnostic panel, not the API service.

Expected successful ingestion: 201 for a new stored event, or 200 when retrying
an identical already-stored event. Pending events are removed only after an
acknowledgment. The code retries transient failures with backoff and retains
pending events. Authorization/configuration failures require correction and
manual Retry. Invalid/conflicting events can be moved to the visible rejected
queue; inspect the reason rather than treating them as uploaded records.

Keep the application foregrounded. Background/closed-app capture is not the
intended demonstration mode. Do not clear queues just to hide a failed test.

   npm run simulate -- --owner porsche --vehicle WP0ZZZ99ZTS392124 --device WP0ZZZ99ZTS392124 --seconds 30

To exercise another independent test stream/session:

   npm run simulate -- --owner porsche --vehicle WP0ZZZY1ZNSA54819 --device WP0ZZZY1ZNSA54819 --seconds 30

For a real phone against a local API, use the laptop's reachable LAN/API tunnel
address, not localhost on the phone. Keep the appropriate firewall/network
access configured. The phone must retain its actual sensor permissions.

9. TROUBLESHOOTING BY OBSERVED ERROR

401 / Token necunoscut / Token expirat:
The token is missing, unknown, invalidly configured, or expired. Match the
original token to the real 64-hex SHA-256 hash in DEMO_TENANTS_JSON. Do not paste
the hash into the phone. Preserve the right token input precedence and remove
an unintended old EXPO_PUBLIC_API_TOKEN fallback. Check auth in /api/health.

403 / Tokenul nu are acces la acest vehicul:
A recognized credential is not permitted for the requested VIN/owner. Keep the
working token/hash and add the exact actual VIN to that entry's vehicleIds.
Preserve ownerId=porsche and other owners' entries. Save Azure settings, allow
the restart, then Retry. Explicit VINs work without relying on wildcard changes.

404 / adresa nu exista:
Compare the phone API URL to Azure's actual defaultHostName. Phone config must
not append /api itself. Verify /api/health and registered functions; deploy the
current src/backend/api package if endpoints are missing. A skipped CD job has
not published code. A root URL 404 alone is not decisive; test the named routes.

503 / database unreachable:
The route exists but backend storage is unavailable. Check SQL_SERVER FQDN,
SQL_DATABASE, schema, the Function App identity grant, and SQL networking. Keep
that identity distinct from the GitHub deployment identity.

Browser fetch/CORS failure:
Use an HTTP(S)-served page and an explicitly allowed Function App origin.
localhost and 127.0.0.1, or different ports, are different origins. Confirm API
availability separately; a browser message alone does not prove CORS is the
only cause. CORS is not the fix for an application-generated native-phone 401.

Empty fleet / no live updates:
Confirm acknowledged records and correct owner/VINs. Set all-vehicle selection,
clear legacy filters, initialize browser auth on this origin, and resume live
polling. Check the dashboard's Network requests, timestamps, and paused status.
A missing GPS fix can leave a route stationary even when other sensors update.

409 / invalid event:
409 means the same event ID was reused with different content. Keep retries
identical. Inspect validation/rejected-event details rather than editing and
resubmitting an old ID as a different measurement.

10. STOPPING THE DEMO

- Stop phone capture/sending with its Stop control and verify its queue state.
- Stop local Expo, API, and web terminals with Ctrl+C.
- From src/backend/api, npm run db:down stops local containers while retaining
  the SQL volume. Do not remove volumes when intending to keep the demo data.
- Clear the browser demo credential after a shared-computer session:

   localStorage.removeItem('verity_drive_auth_v2');

  Run that JavaScript in the dashboard's browser console; it does not delete SQL
  records. Reinitialize browser authentication before the next demonstration.
- Stopping local terminals does not remove or stop billed Azure resources.
  Adina owns post-event resource cleanup after required evidence
